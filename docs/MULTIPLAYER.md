# 真人好友邀戰：手動配置與驗證

目前工作區沒有可用的 Supabase 設定，因此預設為「尚未配置」。單機投籃練習與全部島圖、NBA 模擬賽事及勇士政策挑戰都能直接開啟 `index.html` 使用。沒有配置時，不發送房間請求、不產生假房間、不加入假玩家。

## 手動配置

1. 在你自己的 Supabase 專案啟用 **Authentication → Anonymous Sign-ins**。每個瀏覽器使用獨立的匿名 Auth 使用者，不以暱稱識別身分。
2. 將本專案 `supabase/schema.sql` 的完整內容貼到 Supabase SQL Editor 執行。它只建立 `nba_` 前綴的資料表、函式與權限。此 SQL 尚未連接資料庫執行，須由你手動驗證。
3. 在 `assets/supabase-config.js` 填入 Project URL 與 **publishable key**，或舊版 **anon key**：

   ```javascript
   globalThis.NBA_SUPABASE_CONFIG = {
     url: "https://你的專案.supabase.co",
     publishableKey: "你的公開 publishable 或 anon key"
   };
   ```

   前端不可放入 `service_role`、`sb_secret_` 或資料庫密碼。程式會拒絕服務端金鑰格式。公開金鑰不提供資料表寫入權限，所有寫入經過驗證 Auth 身分的 RPC。
4. 手動重新開啟前端。成功取得匿名身分及真實房間摘要後才顯示「已連線」。若仍未連線，檢查匿名登入、SQL、公開設定及網路；頁面有重新連線入口。
5. 本次變更沒有 push 或部署。跨裝置邀請連結須指向兩台裝置都能讀取的**相同新版前端**。由你之後手動更新 GitHub Pages，或在自己的網路提供這份靜態網站。本機 `file://` 連結無法讓另一台裝置直接讀取你的硬碟。

使用原生 `fetch` 呼叫 Supabase Auth / PostgREST RPC，不依賴 CDN 或 SDK。房間與球場摘要每兩秒讀取一次，不需要 Realtime publication。

## 房間與投籃規則

- 港邊、公園、屋頂共 15 個獨立 `court_id`。每座球場可以同時有多個好友房間；房間不是 NBA 球隊賽事。
- 開房 → 複製指定球場的加入連結 → 第二位真人輸入暱稱加入 → 雙方就緒 → 房主開始。
- 伺服器設定 5 秒倒數，雙方同時各投 30 秒。使用金色瞄準區，空白鍵或觸控出手，最短間隔 0.5 秒，每次命中 1 分。
- 每人 30 秒結束後提交自己的命中數與出手數。資料庫只接受本人一次提交、正確局數、0–60 次出手、命中數不超過出手數；不能代替對手提交。
- 投籃結束後有 15 秒傳輸寬限。雙方已提交即結算；時間到仍缺一方提交，已提交者獲勝並標示對手未提交。雙方均未提交則不計勝負；同分顯示平手。
- 斷線不會生成對手或替代成績。失敗的提交可在截止前重送；超時不能補改。對局途中重新整理會遺失尚未提交的本機出手紀錄，原本的伺服器倒數仍繼續，請完成一局後再整理頁面。
- 房主可在完賽後「再來一局」，局數增加，雙方成績與就緒狀態重設。上一局的延遲提交會被拒絕。
- 房間兩小時到期；同一房主最多五個活躍房間。等待中的第二位離開可騰出空位；房主離開或對戰中離開會取消房間。
- 所有輸贏只讀取房間內的真實提交。這是好友休閒模式，尚未實作逐球伺服器驗證或競賽級防作弊，不應用於有獎金的排名賽。

## 資料庫權限

`nba_rooms` / `nba_players` 啟用 RLS；`authenticated` 僅能讀取自己所屬房間。未授予直接 INSERT、UPDATE、DELETE。

`nba_join_room` 先 `FOR UPDATE` 鎖定房間，再檢查指定球場、重複身分與兩人上限；`(room_id,user_id)` 主鍵及 `(room_id,slot)` 唯一限制提供第二層保護。RPC 使用 `auth.uid()`，不接受可偽造的玩家 ID。成績、就緒、重開均在同一房間鎖下處理。

`nba_court_activity` 只回傳各球場實際等待、準備、對戰中的房間數，不公開其他房間的邀請碼或暱稱。好友房間不提供公開房列表或自動配對；「我的房間」只列出目前身分參與的房間。

## 兩台裝置驗證方法（尚待實際連線驗證）

1. 裝置 A、B 開啟相同的新版網站，確認均顯示已連線。不要用同一瀏覽器的兩個一般分頁冒充不同玩家；它們共享匿名身分。可用兩台裝置，或一般視窗加獨立無痕視窗。
2. A 在「潮汐一號」輸入暱稱並開房。確認只有 A 與一個清楚標示的空位；複製加入連結給 B。
3. B 開啟連結，確認自動定位 `harbor-01`，輸入自己的暱稱並加入。A、B 都應在約兩秒內看到相同兩位玩家。
4. A 在同一個房間重複加入，應收到已加入提示且不新增玩家。第三個獨立身分 C 嘗試相同邀請碼，應收到房間已滿。用另一座球場輸入此邀請碼，應收到球場不符。
5. 兩人尚未就緒時房主不能開始；只一人就緒仍不能開始。兩人都就緒後，由 A 開始，檢查 5 秒倒數及雙方各 30 秒。
6. 分別用空白鍵與觸控投籃。檢查時間到後不能出手；在刻意不同分數下看到正確勝負，再以雙方都不投球測試 0：0 平手。
7. 成績送出後，用自己的匿名身分嘗試對 `nba_players` 直接 PATCH 自己或對方分數，必須被權限拒絕。`nba_submit_score` 沒有對方 ID 參數，不能指定別人。重送同一局成績應收到 `SCORE_ALREADY_SUBMITTED`。
8. A 重開；確認局數 +1、雙方皆未就緒、舊分數清空。用舊局數提交必須收到 `ROUND_MISMATCH`。B 不能代房主開始或重開。
9. 再開一局，讓 B 中斷連線且不提交。30 秒後再等 15 秒寬限，A 應看見 B 未提交與判負；雙方都不提交則不計勝負。任何中斷時都不能出現假玩家或假成績。
10. 在同一球場另外開房，確認房間互不干擾；在另一個球場開房，確認球場狀態不混用。等待／準備／對戰數字須與資料庫真實房間一致。

上述兩裝置同步、匿名 Auth、SQL 實際語法、RLS 與並行入房，均須在你套用設定後實測；終端機模型與 SQL 結構檢查不能取代它們。
